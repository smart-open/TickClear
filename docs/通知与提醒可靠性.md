# 通知与提醒可靠性设计（v2.8X++）

> 本文档说明 TickClear 提醒在「APP 打开 / 后台 / 锁屏」三种状态下的投递模型、可靠性设计与已知限制。
> 对应代码：`domain/scheduler/ReminderScheduler.kt`、`HabitReminderScheduler.kt`、`ReminderReceiver.kt`、`HabitReminderReceiver.kt`、`NotificationHelper.kt`、`BootReceiver.kt`、`FullScreenAlertActivity.kt`。

## 1. 调度模型（单一事实源 = AlarmManager 系统闹钟）

不依赖 WorkManager，改用 `AlarmManager` 精确闹钟，保证定点送达（PRD §7.2 硬性要求），在 WorkManager 不可用环境同样可靠。

- **两个调度器**：`ReminderScheduler`（任务）、`HabitReminderScheduler`（习惯）。
- **排程入口（统一走，避免孤立闹钟）**：
  - `AddTaskUseCase`：先 `cancelForTask` 再 `scheduleForTask`（新建即排，不产生重复/孤立闹钟）。
  - **任务状态变更统一经 `TaskScheduler` 抽象下沉排程**：`UpdateTaskUseCase`（编辑）、`PauseTaskUseCase`/`ResumeTaskUseCase`、`PauseGroupUseCase`/`ResumeGroupUseCase`、`SoftDeleteTaskUseCase`/`RestoreTaskUseCase` 均自动 `cancelForTask` 或 `scheduleForTask`，任何改状态的路径都不会残留/错乱闹钟（此前这些路径完全不碰闹钟，是「暂停仍响 / 恢复不响 / 编辑按旧时间响」的根因）。
  - `BootReceiver`：开机重建渠道 + 重排全部提醒与回收站/位置/自动备份闹钟；**并新增 `MY_PACKAGE_REPLACED` / `TIMEZONE_CHANGED` / `TIME_SET` 广播重排**（见 §7），补齐「非开机但闹钟丢失」盲区。
  - `TickClearApplication`：启动兜底重排（已 `runCatching` 保护，绝不阻断启动）。
  - **接收器触发后续排**：任务 `ReminderReceiver` 弹通知后调 `ReminderScheduler.scheduleNext`；习惯 `HabitReminderReceiver` 调 `HabitReminderScheduler.scheduleNext`。这是重复任务「持续提醒」的关键——曾经缺失会导致重复任务首次响铃后永久停摆。
- **未来发生日预排**：`rescheduleAll` 在 60 天窗口内预排「明天/下周」类单次任务，避免重启/进程被杀后若用户次日不打开 App 则闹钟丢失。
- **永不静默丢弃**：目标时刻已过去时，`resolveTrigger` 对一次性任务给 5 分钟宽限（`now+2s`，迟到提醒优于丢失），对重复任务从次日起重排。

## 2. 精确闹钟权限与三级降级（高优先级 / 习惯走 setAlarmClock）

> ⚠️ **勘误（v2.8X 闪崩修复）**：本节旧版写的「`setAlarmClock` **免** `SCHEDULE_EXACT_ALARM` 权限」是**错误**结论。
> 自 Android 12（API 31）起，`setAlarmClock` 与 `setExact*` **同样受精确闹钟权限门禁**；Android 14 起该权限对新装应用
> **默认拒绝**。当时 `setAlarmClock` 是裸调用（无权限判断、无 try/catch），在无权限设备上抛 `SecurityException`，
> 经 `BootReceiver`（只有 try/finally 没有 catch）变成协程未捕获异常，**开机/覆盖安装后 App 直接闪退**。

**权限声明（Manifest，官方推荐组合）**

```xml
<uses-permission android:name="android.permission.SCHEDULE_EXACT_ALARM" android:maxSdkVersion="32" />
<uses-permission android:name="android.permission.USE_EXACT_ALARM" />
```

- Android 12~12L（31/32）：`SCHEDULE_EXACT_ALARM`，需用户到系统设置手动授予（设置页/任务编辑页有引导入口）。
- Android 13+（33+）：`USE_EXACT_ALARM`，**安装即授予、无需用户操作**——本 App 核心功能为定时任务/习惯提醒（闹钟类），符合其适用范围。授予后 `canScheduleExactAlarms()` 恒为 `true`，UI 里的权限引导自动隐藏。

**三级降级链（`ReminderScheduler.setExact` / `HabitReminderScheduler.setExact` 完全一致）**

| 级别 | API | 条件 | 特性 |
| --- | --- | --- | --- |
| ① | `setAlarmClock` | 有精确闹钟权限 | 绕开 Doze、状态栏显示闹钟图标，到点必响 |
| ② | `setExactAndAllowWhileIdle` | 有精确闹钟权限、① 被系统实时拒绝 | 精确，可能被系统轻度约束 |
| ③ | `setAndAllowWhileIdle` | 无权限 / ①② 均失败 | 非精确（可能延迟数分钟），但绝不丢失 |

- 每一级都用 `runCatching` 包裹并降级到下一级，**任何情况下都不把异常抛给调用方**；连第三级失败也只记日志。
- 权限判断统一走 `canUseExactAlarms(am)`（`SDK < S` 直接 true；`canScheduleExactAlarms()` 异常按 false）。
- **调用侧同样兜底**：`BootReceiver` 的四个重排步骤各自 `runCatching`（单步失败不拖垮后续，也不再冒泡成未捕获异常）；`TickClearApplication`、`DebugViewModel.reschedule` 同理。
- **「稍后」**：`scheduleSnooze` 透传 `level`，高优先级稍后 `useAlarmClock = true` 保持绕 Doze，不被降级。

## 3. 三态触发路径

| 状态 | 投递机制 | 声/震 | 说明 |
| --- | --- | --- | --- |
| **APP 打开（前台）** | Manifest 广播 `ReminderReceiver`/`HabitReminderReceiver`，系统进程弹出通知 | 按渠道 | 前台不影响系统层闹钟投递；仅全屏意图在 Android 14+ 受「额外提醒权限」约束时降级为普通通知 |
| **APP 后台（未杀）** | `setAlarmClock`（高/习惯）精确投递；中/低 `setExactAndAllowWhileIdle` | 按渠道 | 无精确权限时三级降级为非精确，仍响（见 §2） |
| **锁屏** | `setAlarmClock` 保证到点必响；通知经系统栈展示；全屏提醒 `FullScreenAlertActivity` 现已 `showWhenLocked`+`turnScreenOn`，Android 12+ 锁屏直接点亮，Android 14+ 未获「额外提醒权限」时降级为普通通知 | 高优先级 `VISIBILITY_PUBLIC` 显示内容 | 声/震由渠道控制（`setSound`+`enableVibration`）；`mid`/`low` 渠道已补震动与灯 |

> 触发根因：闹钟 = `AlarmManager`（`setAlarmClock`/`setExactAndAllowWhileIdle`）+ Manifest `BroadcastReceiver`（系统级），前台/后台/被杀/锁屏都响，**不依赖 App 进程**。

## 6. Android 13+ 运行时通知授权（三态不响的设备端根因）

`AlarmManager` 调度、渠道、声震全部正常，**但若 App 运行在 Android 13（API 33）及以上且未获运行时 `POST_NOTIFICATIONS` 授权，系统会静默丢弃全部通知**——表现为「APP 打开 / 后台 / 锁屏三种状态都不响」，而日志里触发/渠道/调度都正常（极易误判为调度问题）。

- **必需**：`MainActivity.onCreate` 中通过 `ActivityResultContracts.RequestPermission()` 请求 `POST_NOTIFICATIONS`（低于 13 系统自动放行，无需请求）。
- **Manifest 声明不等于授权**：`POST_NOTIFICATIONS` 自 13 起为**运行时危险权限**，仅 `<uses-permission>` 声明不足以在 13+ 新装/升级后弹通知；用户若拒绝或升级后未弹窗授权，三态通知全部被静默拦截。
- **排查顺序**：① 确认 `AlarmManager` 已排（`setAlarmClock`/精确）→ ② 确认渠道 `importance` ≥ DEFAULT 且高渠道 `setSound`+震动 → ③ **确认 13+ 已获运行时 `POST_NOTIFICATIONS` 授权**（设置 → 应用 → 通知）→ ④ **确认覆盖安装/改时区后已重排**（见 §7）；四者齐备，三态通知方可触发。
- 实证：用户运行日志证实触发/渠道（importance=4）/调度均正常，根因确为缺运行时授权；补授权后三态通知恢复。

## 4. 通知渠道（带版本后缀，可重建）

- 渠道带版本后缀 `v4`（`NotificationHelper.CHANNEL_VERSION`，自 `v3` 升级；`LEGACY_CHANNEL_IDS` 含 5 个 `*.v3` ID，创建时清理，修正旧版中渠道优先级漏配震动的问题）。Android 8+ 渠道不可就地升级，历史静音/无震渠道会永久残留并使新通知静默——靠新 ID 重建修正。
- **高渠道（high）**：`IMPORTANCE_HIGH` + `setSound(notify_chime, USAGE_ALARM)` + `enableVibration(true)` + `setBypassDnd(true)` + `VISIBILITY_PUBLIC`。
- **中渠道（mid）**：`IMPORTANCE_HIGH` + `enableLights(true)` + `enableVibration(true)` + `vibrationPattern`；原 `v3` 中漏配震动，本轮补回。
- **中渠道静音镜像（mid_muted）**：全局「声音」关闭但非高优先级时改投 `CHANNEL_MID_MUTED`（仅震动 + 轻 `vibrationPattern`），解决 Android 8+「声音由渠道决定、无法单条 `setSound(null)`」导致的「关声音仍响铃」死开关；`< O` 走 `builder.setSound(null) + setDefaults(VIBRATE)`。
- **高优先级任务 / 习惯始终响铃+震动**，不受全局「声音」开关约束（`ReminderPrefs.shouldForceSound(level) == "high"`）；低优先级命中静音时段降级为 silent 渠道；中优先级全局静音时改投 mid_muted 仅震动。

## 7. 覆盖安装 / 改时区 / 改时间重排（闹钟丢失盲区，2026-08-01 补）

- **根因**：`AlarmManager` 闹钟在（a）应用覆盖安装（`MY_PACKAGE_REPLACED`）时被系统清空；（b）跨时区（`TIMEZONE_CHANGED`）或手动改系统时间（`TIME_SET`）后 RTC 基准漂移。原 `BootReceiver` 仅听 `BOOT_COMPLETED`，覆盖安装/改时区/改时间后用户不重启则闹钟永久丢失——表现为「改完时区 / 升级后提醒全停」。
- **修复**：`BootReceiver` 新增 `RESCHEDULE_ACTIONS = {BOOT_COMPLETED, MY_PACKAGE_REPLACED, TIMEZONE_CHANGED, TIME_SET}`，`onReceive` 统一判定并重排全部提醒与回收站/位置/自动备份闹钟；Manifest `<intent-filter>` 补齐三类广播。重排前 `AppLogger.w` 留痕便于排查。

## 8. 接收器守卫、一次性完成与「稍后」语义（2026-08-01 补）

- **幽灵通知 / 暂停仍响**：`ReminderReceiver.showNotification` 新增双守卫——① `task.deletedAt != null || !task.reminderEnabled` → `ReminderScheduler.cancelForTask` 并 `return`；② `task.status != TaskStatus.ACTIVE.code`（暂停/一次性已完成）→ 跳过本次但 `scheduleNext` 保链再 `return`。杜绝已删/关提醒/暂停/已完成任务的历史闹钟打扰。
- **一次性任务提前完成后仍响**：`resolveTrigger` 增 `occurrenceDone: Boolean`，一次性任务 `occurrenceDone` 时返回 null；`rescheduleAll`/`scheduleForTask`/`scheduleNext` 均传 `done = inst.status != TaskStatus.ACTIVE.code`，完成即不再重排。
- **「稍后」修复**：`ACTION_SNOOZE` 改用 `instanceId` 取关通知（原误传 `taskId` 致通知不消失），并透传 `level`；`scheduleSnooze` 签名增 `level`，高优先级稍后 `useAlarmClock = true` 保持绕 Doze。
- **`cancelForTask` 多日期撤销**：原 `next == today` 直接 `return` 漏撤未来日，改为遍历 `today` 与 `today+1` 两个发生日（`filter { it != today }`）撤销，避免残留。
- **编辑重排原子化**：`UpdateTaskUseCase` 在 `upsert` 后 `cancelForTask → deletePendingFrom → (reminderEnabled) scheduleForTask`，编辑改时间后立即按新时刻重排，旧实例从「今日」列表清除。

## 5. 已知限制（平台/真机约束，非缺陷）

1. **DND 绕过需用户授权**：`setBypassDnd(true)` 生效前提是用户在系统设置授予「通知优先级访问」权限（`ACCESS_NOTIFICATION_POLICY`）。调试页已新增「勿扰绕过」诊断行与跳转设置入口；未授权时勿扰模式仍会静音高优先级提醒。
2. **进程强杀极端边界**：若进程恰在接收器续排（`scheduleNext`）执行窗口内被强杀，下一次打开 App / 重启由 `rescheduleAll` 兜底补排（覆盖安装/改时区/改时间已由 §7 广播重排覆盖，无需等重启）。
3. **全屏提醒**：Android 14+ 未获「额外提醒权限」时降级为普通通知（系统隐私策略）。
